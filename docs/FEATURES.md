# ACSA Prototype — Features & How It Works

A complete technical reference for what's been built and how each piece works. For the phase-by-phase build history, see [`PROTOTYPE_IMPLEMENTATION_PLAN.md`](./PROTOTYPE_IMPLEMENTATION_PLAN.md). For a presenter's walkthrough, see [`DEMO_SCRIPT.md`](./DEMO_SCRIPT.md).

## What this is

ACSA (Autonomous Container Search Assistant) is a prototype of an AI intelligence layer for container retrieval planning at a shipping terminal, sitting above a Terminal Operating System (TOS). Since there's no real TOS to integrate with, everything — the TOS, the yard, the equipment, the workers, the IoT sensors — is simulated in software. The prototype demonstrates one complete, real workflow end to end:

> A natural-language retrieval request → simulated TOS lookup → deterministic route/equipment optimization → digital-twin conflict validation → AI-generated explanation → confidence scoring → human approval → simulated dispatch → worker confirmation → completed retrieval → dashboard + immutable audit trail.

The central architectural rule, followed throughout: **deterministic algorithms compute; the LLM only interprets and explains.** Route-finding, equipment scoring, and conflict detection are all plain TypeScript algorithms with no AI involvement. Gemini's only two jobs are turning a natural-language sentence into structured fields, and turning an already-computed plan into a readable sentence for a human.

## Architecture at a glance

```
Client (Dashboard / Worker App)
        │  fetch()
        ▼
API routes (src/app/api/**)  — thin HTTP wrappers, no business logic
        │
        ▼
┌─────────────────────────────────────────────────────────────┐
│ pipeline/     → composes search + allocation + route + twin   │
│ agents/       → Gemini: interpret request, explain a plan     │
│ policy/       → confidence/policy gate                        │
│ approval/     → human-in-the-loop workflow + audit log        │
│ worker/       → dispatch → start → confirm → complete         │
│ simulation/   → live demo controls + background drift         │
│ agent-monitor/→ Container Management Agent: detect, rank,     │
│                 raise alerts; apply/dismiss is human-in-loop  │
├─────────────────────────────────────────────────────────────┤
│ search/       optimization/       twin/                       │
│ (cache-first  (A* routing,        (plan validation             │
│  fuzzy match)  equipment scoring)  against live state)         │
├─────────────────────────────────────────────────────────────┤
│ adapters/tos/  MockTOSAdapter — the only module that touches   │
│                "the TOS" (backed by the seeded database)       │
└─────────────────────────────────────────────────────────────┘
        │
        ▼
domain/db.ts (Prisma) → SQLite (dev.db)
```

Every layer only talks to the layer below it through a narrow interface, so any one piece (e.g. `MockTOSAdapter`) could be swapped for a real integration without touching anything above it.

## Data model

Defined in `prisma/schema.prisma`, backed by SQLite (`dev.db`, gitignored — recreated by `npm run db:migrate` + `npm run db:seed`):

| Table | Purpose |
|---|---|
| `Container` | Position (block/row/bay/tier), status, priority, type, weight, destination, retrieval eligibility. TOS-synced cache — never authored by ACSA. |
| `Equipment` | Cranes and yard trucks: type, status (AVAILABLE/BUSY/OFFLINE), capacity, current yard-node position. |
| `YardBlock` / `YardNode` / `YardLane` | The yard graph: named blocks, intersections with real x/y coordinates, and the lanes connecting them (distance, blocked flag, congestion weight). |
| `Worker` | Simulated yard workers with a status and (at most) one active task. |
| `Task` | An ACSA-owned retrieval task, moving through `REQUESTED → PLANNED → APPROVED → DISPATCHED → IN_PROGRESS → RETRIEVED → COMPLETED` (or `REJECTED`). |
| `Recommendation` | The system's proposed plan for a task — route, equipment, confidence score/level, explanation, twin-validation result. |
| `AuditEvent` | Immutable log of every meaningful action (submitted, recommended, approved, rejected, overridden, dispatched, confirmed, status change, agent alert raised/applied/dismissed). Readable via `GET /api/audit` and the `/audit` page. |
| `AgentAlert` | Raised by the Container Management Agent (`src/agent-monitor/`) — type, severity, suggested action, rank/explanation, resolution. Never self-executes; `apply()` calls the same deterministic service a human would use manually. |
| `TosWriteBackLog` | Persists what `MockTOSAdapter.writeRecommendation()` sends "back to the TOS" (previously an in-memory array, lost on restart). |
| `SensorEvent` | Simulated IoT events (RFID checkpoints, etc.) generated by the demo controls. |

`Equipment` also tracks in-progress movement (`movementTargetNodeId`/`movementStartedAt`/`movementArrivesAt`) — a move takes real travel time (computed from the A* route distance) instead of teleporting; `currentNodeId` stays the last *confirmed* position, resolved via `src/domain/equipmentMovement.ts` wherever equipment position is read.

### Synthetic data generator (`prisma/seed.ts`)

Deterministic from a fixed seed (`SEED = 42`, using a mulberry32 PRNG in `src/domain/seed/rng.ts`), so every reseed produces byte-identical data — required for repeatable demos and tests. Generates:

- **1,200 containers** spread across 10 yard blocks (A–J), each with a unique row/bay/tier slot, randomized type/weight/destination/status/priority in realistic proportions.
- **110 pieces of equipment** — 20 cranes and 90 yard trucks — placed on real yard-graph nodes with randomized initial availability.
- **A 16-node, 23-lane yard graph**: a gate, a 5-column "spine" backbone, 10 block-entry nodes (two rows of five), *plus* lateral aisle lanes connecting adjacent blocks in the same row. That last part matters: without them the graph is a pure tree with exactly one path between any two points, so blocking a lane would just strand traffic instead of triggering a real reroute. The lateral lanes give A* actual alternate routes to choose during a live congestion demo.
- **40 workers**, mostly available, some already busy or off-shift.

## Simulated TOS layer

### `TOSAdapter` interface (`src/adapters/tos/TOSAdapter.ts`)

The single interface any code is allowed to use to represent "the TOS." Mirrors what a real integration would expose: `searchContainers`, `getContainer`, `getEquipment`, `getYardState`, `getEvents`, `writeRecommendation`.

### `MockTOSAdapter` (`src/adapters/tos/MockTOSAdapter.ts`)

The only implementation right now, backed directly by the seeded database — but written so a real `NavisTOSAdapter` or `TideworksTOSAdapter` could be dropped in later without any caller changing. Read-mostly: it never writes container or equipment master data, only ever "writes back" a recommendation (matching the report's stated real-TOS integration pattern). Also holds an in-memory feed for simulated TOS-originated events (gate/crane moves).

## Container Search (`src/search/ContainerSearchService.ts`)

A three-tier, fully deterministic lookup, each tier producing a transparent confidence score:

1. **Cache** — an in-memory `Map` that warms as containers are looked up (standing in for a Redis hot path). An exact repeat query is served instantly at confidence 1.0.
2. **TOS exact/substring match** — on a cache miss, queries the mock TOS. An exact ID hit scores 1.0; a substring hit scores based on how much of the container ID the query actually covered.
3. **Fuzzy match** — if nothing matches directly, the query is tried against shrinking prefixes of itself until the TOS returns *some* candidates, which are then ranked by Levenshtein (edit) distance from the original query. This recovers real typos — e.g. a single mistyped digit in a container ID — with a confidence that degrades smoothly as the edit distance grows.

## Route Optimization — A* (`src/optimization/YardGraph.ts`, `astar.ts`, `RouteOptimizationService.ts`)

- `YardGraph` builds an in-memory undirected graph from the yard's nodes and lanes.
- `findPath()` runs A* with edge cost = `distance × congestionWeight`, excluding any blocked lane outright, using straight-line distance as the heuristic (proven admissible: congestion only ever *inflates* real cost above the physical distance, never deflates it, so the heuristic never overestimates).
- `RouteOptimizationService` wraps this with a simple constant-speed ETA calculation.

This is what lets the yard map visibly reroute around a blocked lane or a congestion spike during a live demo — the algorithm genuinely recomputes the cheapest path every time, it isn't scripted.

## Equipment Allocation (`src/optimization/EquipmentAllocationService.ts`)

Deterministic weighted scoring, not an LLM guess and not OR-Tools (unnecessary at this scale):

- **Hard filters** (excluded outright, not scored): wrong equipment type, not `AVAILABLE`, insufficient capacity for the container's weight, or simply unreachable on the yard graph.
- **Scored factors**: distance (via the real A* route, not a straight-line guess), capacity fit (penalizes using an oversized crane for a light container), and live workload — a real count of the equipment's currently active tasks (per the shared `ACTIVE_TASK_STATUSES` constant, including `PLANNED`), not just its status flag.
- **Priority reweighting**: `HIGH`/`URGENT` requests weight distance at 0.6 instead of 0.4 — get the nearest capable resource moving, even at a small cost to capacity-fit precision.
- Every candidate is returned with its full score breakdown, not just the winner, so the UI can show *why* one truck beat the alternatives (and so a supervisor's Override dropdown has real runner-up options to pick from).

## Digital Twin (`src/twin/DigitalTwin.ts`)

Before any plan is ever shown to a human, `validatePlan()` checks it against live state for seven kinds of conflict: container not found / not eligible / already reserved by another task; equipment not found / unavailable / already committed elsewhere; or a blocked lane on the route. "Already committed elsewhere" is checked against `ACTIVE_TASK_STATUSES` (`src/domain/constants.ts`) — `PLANNED, APPROVED, DISPATCHED, IN_PROGRESS`. Deliberately includes `PLANNED`, not just post-approval states: a resolved-but-not-yet-approved recommendation already names an equipment/container pair, so without it a second concurrent request could get scored, twin-validated, and persisted against the same equipment while an earlier request just sits awaiting supervisor approval. The constant is shared with `EquipmentAllocationService`'s workload scoring so the two checks can't drift out of sync with each other. Each result is classified:

- **PROCEED** — no issues, plan stands.
- **REPLAN** — a mechanically fixable conflict (busy equipment, a blocked lane) — the pipeline automatically retries with the next-best candidate before giving up.
- **ESCALATE** — something a retry can't fix (a bad container state, missing equipment) — surfaced directly rather than looped on.

## Retrieval Planning Pipeline (`src/pipeline/RetrievalPlanningPipeline.ts`)

The composition point that wires search → equipment allocation → routing → twin validation into one deterministic flow, with built-in self-correction: if the top-ranked equipment fails validation for a replannable reason (e.g. a concurrent request claimed it first), the pipeline automatically tries the next-best candidate — up to 5 attempts — before surfacing a result. Possible outcomes: `READY`, `AMBIGUOUS` (multiple plausible containers, no clear winner), `NOT_FOUND`, `NO_EQUIPMENT`, `NO_ROUTE`, or `NEEDS_ESCALATION`.

## Agent Orchestration — Gemini (`src/agents/`)

> **Deviation from the source spec:** the report specifies Claude for this layer. At the project owner's explicit direction, this prototype uses Google's Gemini API instead (`gemini-flash-latest` — the model named in the original API listing, `gemini-2.5-flash`, was retired for new keys mid-project). The agent layer depends on a small `GenerativeModelClient` interface, not the Gemini SDK directly, so swapping providers only touches `GeminiClient.ts`.

- **`RequestInterpreter`** — turns a sentence like *"Get MSKU1234567 out as quickly as possible"* into `{ containerQuery: "MSKU1234567", priority: "URGENT" }` using Gemini's structured JSON output. It decides *what* to look up, never computes anything itself.
- **`PlanExplainer`** — takes an already-fully-computed plan (container, equipment + score, route, twin result, confidence) and writes 2–4 plain-language sentences about it. Every number in its prompt came from the deterministic layers above; it invents nothing.
- **`RetrievalRequestService`** (`src/pipeline/RetrievalRequestService.ts`) — orchestrates interpret → pipeline → explain, short-circuiting to a clarifying question if the request doesn't resolve to a usable container query. (Reconciled from an earlier, disconnected `RetrievalAgent` scaffold into this single real entry point.)
- **`fallback.ts`** — if Gemini is unavailable (no API key, network error, or — a real occurrence during this project's build — a free-tier daily quota limit), the API layer falls back to a deterministic interpreter (regex-extracts an ISO-6346-shaped container ID from the sentence, keyword-matches urgency language) and a templated explanation, so the app never simply fails a request over an LLM hiccup.

## Container Management Agent (`src/agent-monitor/`)

A second, independent agent layer — not part of the per-request pipeline above. Runs on its own opt-in cycle (never auto-starts, same principle as `SimulationEngine`) watching live yard/task state and raising ranked, explained alerts for a supervisor to act on. Control room at `/agent`.

- **Detectors** (`src/agent-monitor/detectors/`, seven, all deterministic plain TypeScript): `blockedLaneImpact` (a blocked lane actually sitting on an active task's route), `agingTask`, `idleEquipmentBacklog` (a REQUESTED task where equipment is now viable), `congestionHotspot` (sustained over N consecutive cycles, not a single noisy reading), `equipmentTaskMismatch` (equipment BUSY with no task actually claiming it), `urgentContainerUnactioned`, and `unclaimedPriorityContainer` (HIGH/URGENT containers nobody has ever requested — the agent proactively initiating work, capped at 5/cycle). Each detector returns only a fixed `SuggestedActionType`, never free-form text.
- **Ranking** — `AlertRanker` (Gemini) scores/orders/explains the *fixed* candidate list the detectors already produced; it cannot invent a new issue or a different action, and out-of-range model responses are dropped. `AlertRankerFallback.fallbackRank` (severity-weighted, templated explanation) is used when no model is available or the model throws — same degrade-gracefully pattern as the request pipeline's agents.
- **`AgentAlertService`** — the one place a suggested action is ever dispatched (`apply()`), each type mapped to one real deterministic service call (`DemoControls`, `SupervisorApprovalService`, `WorkerTaskService`); `ESCALATE_TO_SUPERVISOR` has no automated action by design. Fails closed: if the underlying call throws, the alert stays open and the error propagates. Every raise/apply/dismiss writes an `AuditEvent`.

## Confidence / Policy Gate (`src/policy/ConfidenceGate.ts`)

A transparent composite score for any `READY` plan — explicitly *not* claimed to be statistically validated, matching the report's own caveat about this kind of decision-support number:

- **searchConfidence** (weight 0.35) — how sure the container match was.
- **equipmentScore** (weight 0.35) — the allocation score for the chosen equipment.
- **routeCongestionCertainty** (weight 0.30) — derived from the average congestion weight along the computed route; a heavily congested route makes the ETA estimate less trustworthy.

Composite ≥ 0.8 → **HIGH**, ≥ 0.5 → **MEDIUM**, else **LOW**. All three factors and their individual contributions are shown, not just the final label.

## Supervisor Approval Workflow (`src/approval/SupervisorApprovalService.ts`)

The only module that persists `Task`/`Recommendation`/`AuditEvent` rows. `submitRequest()` runs the pipeline and only creates a `Task` once a container actually resolves — an `AMBIGUOUS` or `NOT_FOUND` result has nothing to attach a task to, though a `REQUEST_SUBMITTED` audit event is still logged either way (even denied/inconclusive requests get audited). For a `READY` plan, it also persists the `Recommendation` and confidence score.

Three actions, each logging an `AuditEvent`:

- **`approve(taskId, actor)`** → `APPROVED`
- **`reject(taskId, actor, reason)`** → `REJECTED`, reason recorded
- **`override(taskId, actor, reason, newDecision)`** → captures *who* overrode, *why*, the *original* recommendation (equipment/route/confidence, snapshotted from the database), and the *new* decision — all in the audit trail, matching the report's explicit override-tracking requirement.

## Worker Task Lifecycle (`src/worker/WorkerTaskService.ts`)

Carries an `APPROVED` task the rest of the way:

- **`dispatch()`** — assigns the first available worker, marks them `BUSY`, moves the task to `DISPATCHED`. The find-an-available-worker read and the claim-that-worker write happen inside one Prisma interactive transaction, not a read followed by a separate write — otherwise two concurrent `dispatch()` calls could both read the same available worker before either commits, double-assigning that worker to two different tasks. SQLite serializes concurrent write transactions, so wrapping the read+claim in a single transaction closes that window.
- **`startTask()`** — `DISPATCHED → IN_PROGRESS`.
- **`confirmRetrieval()`** — `→ RETRIEVED`, frees the worker, and updates the container's own status/eligibility (the one place ACSA writes container data — reasoned through explicitly in code: there's no separate real TOS in this prototype to have written it first, so this *is* the simulated equivalent of "the move got captured in the TOS's own audit trail").
- **`completeTask()`** — `RETRIEVED → COMPLETED`.

Every transition is guarded (wrong status, wrong worker) and throws rather than silently no-op'ing. `getActiveTaskForWorker()` returns at most one task, matching the report's deliberately minimal worker-app design.

## Live Simulation & Demo Controls (`src/simulation/`)

- **`DemoControls`** — one-shot operator actions: block/unblock a lane, spike or gently drift congestion, reset it, move a piece of equipment (to a specific node or a random neighbor), set or randomly flap equipment availability, trigger a simulated RFID checkpoint event.
- **`SimulationEngine`** — an interval-driven background loop that randomly performs one of the above every few seconds, for continuous ambient yard activity. **Deliberately opt-in**: it never starts itself — only an explicit "Start Background Simulation" click starts it — specifically so it can never interfere with the test suite or an idle dev session.

## API Layer (`src/app/api/`)

Thin route handlers with no business logic beyond wiring — every route just calls into the services above and shapes the JSON response. Errors thrown by the service layer are mapped to a JSON response by a shared `errorResponse()` helper (`src/app/api/errorResponse.ts`) rather than each route re-implementing the mapping: a Prisma "record not found" (`P2025`, e.g. an id that doesn't exist) becomes HTTP 404, every other thrown error (guard rejections, validation failures) becomes 400.

| Route | What it does |
|---|---|
| `POST /api/retrieval-requests` | The main entry point: interpret → pipeline → persist → explain, in one call. |
| `GET /api/tasks`, `GET /api/tasks/[id]` | Task list (optionally `?status=PLANNED,REQUESTED` for the Approval Queue) / single task with full detail (container, equipment, worker, recommendations, audit trail). |
| `POST /api/tasks/[id]/{approve,reject,override,dispatch,start,confirm,complete}` | The approval and worker-lifecycle actions. |
| `GET /api/yard` | Yard graph (nodes/lanes/blocks), equipment, and aggregate stats for the dashboard. |
| `GET /api/equipment` | Fleet list with per-equipment active-task workload — the number `EquipmentAllocationService` already computed internally, now surfaced. |
| `GET /api/workers`, `GET /api/workers/[id]/active-task` | Worker roster (with each worker's current active task, if any) and the worker app's single-task view. |
| `GET /api/audit` | `AuditEvent` list, filterable by `taskId` and/or `action` — every mutating service already wrote these, this is just the read side. |
| `GET/POST /api/agent/{start,stop,status,config}`, `GET /api/agent/alerts`, `POST /api/agent/alerts/[id]/{apply,dismiss}` | Container Management Agent control and alert lifecycle. |
| `POST /api/simulation/{start,stop,status,congestion,block-lane,unblock-lanes,move-equipment,rfid-event,equipment-status}` | The live demo controls. |

## Dashboard & Worker App (`src/app/page.tsx`, `src/app/worker/page.tsx`)

A dark, always-on "ops console" theme (not adaptive to system light/dark — a deliberate branding choice for a dedicated operations tool):

- **Sidebar** — real navigation to every section that exists (Dashboard, Container Search, Operations, Approval Queue, Equipment, Workers, Audit Trail, Simulation, Agent, each with active-state highlighting); sidebar items for sections that still don't exist (Alerts as a unified cross-page feed, Analytics, Settings) are clearly marked and show a dismissing "not built yet" toast on click rather than doing nothing.
- **Shift-Start Overview** — a row of clickable cards above the stat row answering "what needs me right now": pending approvals, aging/unactioned alerts, open alerts by severity, blocked lanes, equipment/worker availability — each linking straight to the page that acts on it. Derived from data already being polled, no extra endpoints.
- **Stat row** — total containers, containers currently in yard, active tasks, equipment availability, crane utilization, average congestion — all real aggregate queries, no placeholder numbers.
- **Yard Map (Live)** — a real 2D SVG rendering of the actual yard graph (the same node coordinates and lane topology A* uses, not a decorative illustration). Equipment markers smoothly animate to their new position whenever `currentNodeId` changes between polls; lanes are colored by real congestion weight and dashed when blocked; the most recently computed route is highlighted with a looping marker labeled "Planned route" (not implying live GPS tracking, since it isn't one).
- **Retrieval Request / Container Details / AI Recommendations** — the three-column heart of the demo: submit a request, see the resolved container, see the equipment/route/twin/confidence recommendation with a full factor breakdown, and the Approve/Reject/Override controls.
- **Status stepper** — the task's real state machine (`REQUESTED → PLANNED → APPROVED → DISPATCHED → IN_PROGRESS → RETRIEVED → COMPLETED`) as a horizontal progress indicator.
- **Simulation Controls** — buttons for every `DemoControls` action plus the background-simulation toggle.
- **Task Tracking** — a live table of every task with an inline "Mark Completed" action for anything sitting at `RETRIEVED`.
- **Approval Queue** (`/tasks`) — every `REQUESTED`/`PLANNED` task in one place, sorted by priority then age (oldest first within a priority), with an "aging" tag once a task passes the agent's own aging threshold. Inline Approve/Reject/Override, plus a bulk "Approve all high-confidence" action. `REQUESTED` tasks with no automatic plan get a manual equipment-assignment form instead of Approve. Read-only for non-SUPERVISOR sessions.
- **Equipment** (`/equipment`) — fleet list (cranes/trucks, filterable) with status, capacity, current location, and active-task workload, so an overloaded piece of equipment is visible without digging into allocation scoring.
- **Workers** (`/workers`) — roster with status and current active task, if any.
- **Audit Trail** (`/audit`) — every `AuditEvent`, filterable by task or action type; task rows link here pre-filtered to that task's own history.
- **Worker App** (`/worker`) — pick a worker, see their one active task (if any), Start → Confirm Retrieval.

Both pages poll the relevant API routes every 5–8 seconds for live updates, with a real ticking clock and a real alert count (blocked lanes + digital-twin conflicts) in the header. Key interactive controls (the retrieval request input, the override equipment select and reason field, the worker picker) carry explicit `aria-label`s rather than relying on placeholder text alone, since placeholder-only labeling disappears for screen readers once the field has a value.

## Testing

Automated tests (Vitest), all run against the real seeded SQLite database — no mocked business logic anywhere in the suite. Notable pieces:

- A synthetic 4-node cycle graph precisely proves A*'s reroute-around-a-blocked-lane and congestion-aware detour selection.
- A live integration test that actually calls the real Gemini API when a key is configured (skips visibly, not silently, if the free-tier quota is exhausted — which happened for real during development).
- `src/e2e/full-demo-scenario.test.ts` drives the *actual Next.js route handlers* — not the underlying service classes — through the complete report scenario end to end, asserting the full seven-event audit trail is present, in order, with no gaps.
- Tests that mutate shared seeded rows (equipment status, lane congestion, task assignments) snapshot the original state and restore it in `afterEach`/`afterAll`, a pattern established after a real flaky-test bug was found and fixed: Vitest's default file parallelism was racing multiple test files against the same database rows.
- `EquipmentAllocationService.test.ts` and `DigitalTwin.test.ts` cover the `PLANNED`-counts-as-active fix directly: a `PLANNED` task holding a piece of equipment now shows up both as workload in allocation scoring and as a reservation conflict in twin validation. `WorkerTaskService.test.ts` covers `dispatch()`'s transactional worker-claim under concurrent calls.

### Continuous integration

`.github/workflows/ci.yml` runs on every push and pull request targeting `main`: install → apply migrations → seed → `next build` (also generates the route types `typecheck` depends on) → `typecheck` → `lint` → `test`, on Node 20/ubuntu-latest.

## Bugs found by actually running the app (not just the test suite)

Several real defects were caught specifically by driving the live UI rather than relying on automated tests — worth recording because it demonstrates why both matter:

- **A crash in the yard map's route animation.** A transient render (reproduced with React's Strict Mode double-invoked effects) could send the animated route marker's array index negative, throwing and unmounting the entire page. Fixed with a defensive guard and lower-bound clamp.
- **A missing "mark complete" button.** The backend and its route handler both worked correctly, and were even covered by the end-to-end test — but that test calls the API directly, so it never noticed the dashboard had no button that ever called it. A task confirmed by a worker had no way to reach `COMPLETED` through the actual UI until this was found and fixed.
- **A dead sidebar.** Half the navigation items gave zero feedback on click — the "not built yet" sections were inert, and the working section links scrolled such a small distance (on a dashboard that mostly fits one screen) that clicking them looked like nothing happened. Fixed with visible active-state highlighting and a toast for the disabled items.
- **A naive fallback interpreter.** When Gemini's quota was exhausted mid-demo, the deterministic fallback initially used the *entire* sentence as the search query, so "Retrieve X as quickly as possible" failed to match anything. Fixed to extract just the container-ID-shaped token from the sentence.

## Tech stack

- **Framework**: Next.js 16 (App Router, TypeScript, Turbopack)
- **Database**: SQLite via Prisma 7 (driver-adapter pattern), seeded deterministically
- **AI**: Google Gemini API (`@google/genai`)
- **Testing**: Vitest, run serially against the real seeded database
- **UI**: Plain CSS Modules, no component library — a hand-built dark ops-console theme with a live SVG yard-map visualization
- **CI**: GitHub Actions (`.github/workflows/ci.yml`) — build, typecheck, lint, test on every push/PR to `main`

## Running it

```bash
npm install
cp .env.example .env        # add GEMINI_API_KEY if you have one — optional, see fallback above
npm run db:migrate
npm run db:seed
npm run dev                  # http://localhost:3000 (dashboard), /worker (worker app)
```

`npm run test` / `npm run typecheck` / `npm run lint` / `npm run build` all pass clean. See [`DEMO_SCRIPT.md`](./DEMO_SCRIPT.md) for a full guided walkthrough.
